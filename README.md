# Splunk App for Data Science and Deep Learning

Splunk App for Data Science and Deep Learning (DSDL) 5.2.5 formerly known as Deep Learning Toolkit for Splunk (DLTK) versions 2.3.0 - 3.9.0 and (DSDL) 5.0.0 - 5.2.5 published on [splunkbase](https://splunkbase.splunk.com/app/4607/).
There is also a prior DLTK version 4.x which was open sourced on [GitHub](https://github.com/splunk/deep-learning-toolkit) but is not actively maintained. Please make use of the latest version 5.2.5

This branch builds the consolidated **5.2.5** container images (see [Images](#images), [Upgrading from 5.2.4 and the 5.2.5 test images](#upgrading-from-524-and-the-525-test-images) and the build report in [BUILD.md](BUILD.md)). They replace the **5.2.5 test images**: the `splunk/mltk-container-*:5.2.5` images pushed to Docker Hub in September 2026 from the original v5.2.5 branch for testing, never released with the DSDL app. Comparisons below refer to those test images.

# About
This repository contains the collection of resources, scripts, and testing frameworks that are used build and deploy the default container images used by the DSDL app. It can be used to modify, secure, update and change these containers and their build process to meet the needs of your enterprise environment.

## Resources
This repository contains the container endpoint (`./app`), jupyter notebook configuration (`./config`) and examples (`./notebooks`, with an overview of what each notebook does and the images it works in: [notebooks/README.md](notebooks/README.md)), build scripts and the main Dockerfiles to create the [existing pre-built container images](https://hub.docker.com/u/splunk?page=1&search=mltk-container) for TensorFlow, PyTorch, NLP libraries and many other data science libraries for CPU and GPU.

### Images
From 5.2.5 all DSDL images are built from one multi-stage template (`docker/Dockerfile`) on Red Hat UBI 9 with Python 3.12. Images that only differed in their library mix were merged; the 5.2.x image names and `images.conf` stanzas keep working because the merged images are also published under the old names.

| Build target | Replaces (5.2.x names, still published) | Platforms | Contents |
| --- | --- | --- | --- |
| `cpu` | `golden-cpu`, `golden-cpu-arm` (`golden-cpu:<v>-arm64`), `escu-cpu`, `golden-cpu-transformers` | amd64, arm64 | classic ML, TensorFlow and PyTorch (CPU), transformers, spaCy 3, Japanese tokenizers, ESCU pretrained models |
| `llm` | `ubi-llm-rag` (stanza `llm-rag`) | amd64, arm64 | the `cpu` content plus llama-index, vector stores and LLM provider SDKs |
| `agentic` | `ubi-llm-rag:agentic-ai-<v>` (stanza `agentic-ai`) | amd64, arm64 | the `llm` image serving the agentic API (`app/main_agentic.py`) |
| `gpu` | `golden-gpu`, `golden-gpu-transformers` | amd64 | PyTorch 2.13 and TensorFlow 2.21 from wheels on the CUDA 12.9 user space it shares with `rapids`, peft/bitsandbytes/accelerate, TimesFM; also runs without a GPU |
| `rapids` | `golden-gpu-rapids` | amd64 | NVIDIA RAPIDS 26.10 (cuDF, cuML, cuGraph) and PyTorch 2.13 from pip wheels on CUDA 12.9, with pandas 3.0 (a RAPIDS requirement) |
| `spark` | `spark` | amd64, arm64 | the `cpu` image plus a headless Java 21 runtime and PySpark 4.2 |

**GPU support.** The `gpu` and `rapids` images share one CUDA 12.9 user space from the NVIDIA wheels (cuda-toolkit 12.9.1, cuDNN 9.20, NCCL 2.29). This is the CUDA that RAPIDS 26.10 is built with (`rapidsai/base:26.10-cuda12`); in the 5.2.5 test images the three GPU images ran CUDA 12.4, 11.3 and 12.2 base images. No CUDA and no cuda-compat are installed in the OS layer, so the images rely on CUDA minor-version compatibility.

- **Driver:** R535 or newer (`NVIDIA_REQUIRE_CUDA=cuda>=12.2`, the RAPIDS 26.10 minimum), R570 or newer for Blackwell (R575+ for B300). R535 and R570 are end of life; use R580 (LTSB) or a newer supported branch. The NVIDIA container toolkit enforces the minimum with `docker run --gpus`; in CDI mode an older driver fails at CUDA initialisation instead.
- **GPUs:** Turing (sm_75, e.g. T4) to Blackwell. PyTorch 2.13 (`+cu129`, the newest PyTorch with a CUDA 12.9 build; torch 2.14 has CUDA 12.6 and CUDA 13 builds only) ships kernels for sm_75, sm_80, sm_86, sm_90, sm_100 and sm_120. **Maxwell, Pascal and Volta GPUs (e.g. M60, P100, P4, V100) are not supported:** the PyTorch build has no kernels for them, and cuDNN 9.20 supports Turing and newer only, which also applies to TensorFlow's convolutions and RNNs. In the 5.2.5 test images, `golden-gpu` (torch cu121) covered sm_50 to sm_90 and `golden-gpu-transformers` (torch cu128) sm_70 to sm_120. In `rapids`, cuDF, cuML and cuGraph still run on Volta; PyTorch in the same image does not.
- **TensorFlow 2.21** (built with CUDA 12.5) uses the same CUDA 12.9 libraries. It has no native Hopper or Blackwell kernels. On Hopper it JIT-compiles its PTX, which may need a driver newer than R535 (not verified). On Blackwell its XLA compiler, which Keras 3 uses on a GPU by default, fails (tensorflow/tensorflow#111958, fixed in TensorFlow 2.22): use PyTorch there. Set `TF_FORCE_GPU_ALLOW_GROWTH=true` when TensorFlow and PyTorch share a GPU in one process. The image imports Triton (used by bitsandbytes and `torch.compile`) before TensorFlow, because importing it after TensorFlow crashes the process; both bundle LLVM (`docker/finalize-venv.sh`).
- **PyTorch 2.13** is one release behind the CPU images (2.14.1). The cu129 build is a Linux-only build outside PyTorch's support matrix and 2.13 gets no patch releases; the hardening in the PyTorch 2.14.0 security notes is not in it. A CUDA 13 line (PyTorch 2.15+, RAPIDS cu13, driver R580+; TensorFlow CPU-only until TensorFlow ships CUDA 13 wheels) is the planned next step.

**Transformer base models.** The bert/T5 base models that the DSDL text classification and summarization assistants and `bert_phishing` load (`app/model/data/classification/...`, `app/model/data/summarization/...`) are not shipped: in 5.2.x they were Git LFS pointer files and never real models either. Place the models on the `/srv` volume under `/srv/app/model/data/`; the container start keeps them. `testing/test_2_transformers.py` needs them. `golden-cpu-transformers` is therefore the `cpu` image under its 5.2.x name (same layers, no extra download). `transformers_classification`, which failed to import in every 5.2.5 test image, imports again in all images, and `transformers_summarization` again in `cpu`, `spark` and `rapids` (the `golden-cpu`, `golden-cpu-arm`, `escu-cpu`, `golden-cpu-transformers`, `spark` and `golden-gpu-rapids` test images could not import it).

`images.toml` is the single source of truth for targets, platforms, published names, stanza ids, titles and runtimes. `tools/render.py` generates `docker-bake.json` and `images_conf_files/images.conf` from it.

### How the images are hardened
- **No build tools at runtime.** Compilers, `-devel` packages and kernel headers exist only in the `builder` stage. In the 5.2.5 test images they caused about 75 % of all scanner findings.
- **Minimal OS.** The runtime is an exact list of about 70 UBI RPMs installed into a `ubi-micro` root (`docker/rootfs/`): no package manager, PAM, `su`/`sudo`, ssh client, Node.js, setuid binaries or second Python. The build fails if the RPM set changes (`docker/rootfs/allow.txt`, and `allow-jre.txt` for the Java runtime of the Spark image) or if an installed RPM is missing files.
- **Locked dependencies.** Every Python package is pinned in a `uv.lock` (`deps/<profile>/`), resolved for Python 3.12; the build fails if a lock is out of date. Every downloaded wheel and sdist is checked against its sha256 in the lock. The two local packages (`package-dsdlsupport`, `vendor/timesfm`) and pure-Python sdists are built from source with version-pinned build backends. PyPI is the only default index; the PyTorch index serves only `torch`. The `gpu` image takes `torchvision` from a direct PyTorch URL, because the CUDA 12.9 index publishes it without a hash; the lock records its sha256.
- **No shared secrets.** No TLS private key is baked into the images (see Certificates). `/etc/passwd` is read-only; arbitrary UIDs (OpenShift) are supported through nss_wrapper.
- **Pinned bases.** Base images are pinned by digest (`tools/update-digests.sh`); rebuild monthly so OS and Python fixes reach the images.

### Building containers
Requirements: Docker with buildx (Docker Desktop, or Docker Engine 25+ with the buildx plugin). A local build loads one platform into Docker: a 5.2.x name builds the platform it was published for, a target name the host's platform if the target supports it. `PLATFORM=linux/amd64` (or `linux/arm64`) selects another platform; building a foreign platform needs QEMU (`docker run --privileged --rm tonistiigi/binfmt --install all`) and is slow. `PLATFORM=all` and `--push-rebuild` build every declared platform and need the containerd image store (Docker Desktop: Settings > General) or a `docker-container` buildx builder (`docker buildx create --use`).

```
./build.sh                               # list targets and published names
./build.sh golden-cpu                    # 5.2.x name: builds the cpu target for linux/amd64
./build.sh golden-cpu-arm                # cpu target for linux/arm64, tagged golden-cpu:<v>-arm64
./build.sh cpu local_build/ 1.0.0        # a target name: the host's platform
PLATFORM=all ./build.sh cpu              # all platforms of the target
./build.sh all splunk/ 5.2.5             # every target
./build.sh --push-rebuild all splunk/ 5.2.5          # rebuild every platform, push with SBOM and provenance (also --push)
PLATFORM=all ./build.sh all splunk/ 5.2.5            # build every platform locally, test, then:
./build.sh --push-only --dry-run all splunk/ 5.2.5   # check what would be pushed
./build.sh --push-only all splunk/ 5.2.5             # push exactly the tested local images
```

Two ways to publish. `--push-rebuild` (the same as `--push`) builds every declared platform again and pushes with SBOM and provenance attestations; what it pushes is a new build of the same commit. `--push-only` pushes the images that are loaded locally, exactly as they were built and tested, without a rebuild and without attestations (a local `--load` keeps none). It first checks every published tag of the requested targets: each must exist locally with all declared platforms (build with `PLATFORM=all`) and carry the version label of the push; otherwise nothing is pushed. Both create the single-platform aliases (`golden-cpu:<v>-arm64`) from the pushed index. `docker login` first.

Every build writes `images_conf_files/images.conf` with the stanzas of the images it built; copy them to `<splunk>/etc/apps/mltk-container/local/images.conf` to make the images available in the DSDL app.

### Changing the Python libraries of an image
1. Edit the profile in `deps/<profile>/pyproject.toml` (`cpu`, `llm`, `gpu-cu12` or `rapids-cu12`). Declare top-level intent only; add an upper version cap only with a comment explaining why.
2. Run `tools/lock.sh <profile>` to resolve the hashed lock (`tools/lock.sh --upgrade <profile>` moves everything to the newest allowed versions, `tools/lock.sh --check` verifies that all locks are current).
3. Rebuild, then run the smoke test and the scan (below).

To build your own image, add a profile in `deps/`, a target stage at the end of `docker/Dockerfile` and a `[targets.<name>]` entry in `images.toml`, then run `tools/render.py`.

### Certificates
The API (port 5000) and JupyterLab (port 8888) use HTTPS unless `ENABLE_HTTPS=false`. At every start the container uses, in this order:
1. the certificate and key given by `API_SSL_CERT` and `API_SSL_KEY` (for example mounted from a secret),
2. `/dltk/.jupyter/dltk.pem` and `/dltk/.jupyter/dltk.key` if a derived image provides them,
3. a self-signed pair generated for this installation into `/srv/.dsdl/tls` (valid for one year; regenerated at container start when it expires within 30 days or does not match its key, so a container that runs for a year needs a restart). Group 0 may read and replace it, so the volume can move to another UID (OpenShift, Kubernetes `runAsUser`). If the directory cannot be written, for example because an earlier build created it for another UID, the container uses a certificate generated for this container only and logs a warning.

If `API_SSL_CERT`/`API_SSL_KEY` are set but the files do not exist, the container logs a warning and continues with option 2 or 3.

Images up to 5.2.4 and the 5.2.5 test images contained a private key generated at build time, shared by everybody who pulled the same image. If you rely on those images, provide your own certificate.

### Installing extra Python packages in DEV mode
The image content is read-only. In a running container `pip install <package>` (in a notebook or a Jupyter terminal) installs into `/srv/.dsdl/site-packages` on the persistent volume, and its command line tools land in `/srv/.dsdl/site-packages/bin`, which is on `PATH`. That directory is searched after the image's own packages, so it can add packages but not replace the image's versions. pip installs the package's dependencies into that directory too, even when the image already has them; use `pip install --no-deps <package>` when the image provides the dependencies. Only pure-Python packages and wheels can be installed: the images have no compiler.

For permanent changes, edit the profile and rebuild, or derive an image: `FROM splunk/mltk-container-golden-cpu:5.2.5`, `USER root`, `RUN pip install <package>` (installs into the image's environment), `USER 1001`.

### Upgrading from 5.2.4 and the 5.2.5 test images
The 5.2.x image names and `images.conf` stanzas keep working, but the contents changed. The earlier values named below are those of the 5.2.5 test images; 5.2.4 differs in details (for example `golden-cpu-transformers` 5.2.4 ran Python 3.9 on Debian 11):

- **Platform:** all images run Red Hat UBI 9 with Python 3.12 (the 5.2.5 test images used Python 3.8 to 3.11 on UBI 9, Debian 11/13 and Ubuntu 20.04/22.04). There is no conda, no R, no Node.js, no compiler, no `curl`/`wget`/`openssl` command line tools, and no ssh client (`git` works over HTTPS only). The runtime user is 1001 with group 0 in every image, including RAPIDS (5.2.5 test images: `rapids:conda`). `HOME` is `/srv/.dsdl-home` on the persistent volume.
- **Major library versions:** TensorFlow 2.21 with Keras 3 (Keras 2 models load through `tf_keras`), PyTorch 2.14 (2.13 in `gpu` and `rapids`, the newest release with a CUDA 12.9 build), transformers 5, scikit-learn 1.9, numpy 2.5, pandas 2.3 (the `spark` and `agentic-ai` 5.2.5 test images had pandas 3.0; `rapids` now has pandas 3.0), spaCy 3.8 with `en_core_web_sm`, xgboost 3.4, LangChain 1.x / LangGraph 1.2 / MCP 1.30 in the llm images (llama-index stays on 0.12), Spark 4.2 with Java 21. **Models persisted with 5.2.4 or the 5.2.5 test images (pickles, Keras 2 files) may need re-saving or retraining.**
- **Removed libraries** (not imported by the shipped models and notebooks, except the deprecated ones, or broken in every 5.2.5 test image): pymc3/theano-pymc, dask-xgboost (it forced xgboost 0.90), spaCy 2 and spacytextblob 0.1, tf2onnx, PyPDF2 (use pypdf), wandb, pydgraph, torch-geometric, pygod, pytorch-tabular, and in the llm images the deprecated LlamaIndex integrations (llama-index meta package, `llms-gemini`/`embeddings-gemini`/google-generativeai (replaced by Google GenAI), Vertex, Databricks, vLLM, instructor embeddings, the agent/program/question-gen OpenAI packages, arxiv, the Neo4j graph/vector stores, `llms-huggingface`, `llms-openai-like`, `llms-deepseek`). Each profile in `deps/` documents the reason.
- **Spark:** local mode only. The Hive metastore and `enableHiveSupport()`, the embedded Derby database, the Thrift JDBC server, Spark Connect, the Scala/R shells (`spark-shell`, `sparkR`, `spark-sql`, `beeline`) and the R kernel of the jupyter base image of the 5.2.5 test images are not included (`docker/spark-jars-trim.txt`). Bundled netty, Jackson and lz4-java jars are replaced by patched releases (`docker/spark-jar-overrides.txt`).
- **GPU:** CUDA 12.9 from wheels, the CUDA of RAPIDS 26.10, in `gpu` and `rapids` (5.2.5 test images: CUDA 12.4, 11.3 and 12.2 base images). Turing to Blackwell for PyTorch and RAPIDS (TensorFlow 2.21: not on Blackwell); Maxwell, Pascal and Volta GPUs (e.g. V100, P100) are no longer supported (see [Images](#images)).
- **Certificates:** no private key is built into the images any more; see [Certificates](#certificates).
- **MLflow UI (DEV mode):** MLflow 3 stores runs in `/srv/mlflow.db` (SQLite). A 5.2.x file store in `/srv/mlruns` that holds runs, experiments or registered models is migrated into it once at the first start; `/srv/mlruns` itself is kept unchanged. If the migration fails, the UI keeps using the file store and the log shows the command to migrate it by hand. The UI runs one worker without MLflow's job runner (`MLFLOW_WORKERS`, `MLFLOW_SERVER_ENABLE_JOB_EXECUTION` change that). MLflow's protection against DNS rebinding and cross-site requests stays on: a browser on localhost has full access, other host names are refused, and through a private address the run lists fail. To open the UI through the Docker host's name or address, set `MLFLOW_SERVER_ALLOWED_HOSTS` (e.g. `dsdl-host.example.com:6060`) and `MLFLOW_SERVER_CORS_ALLOWED_ORIGINS` (e.g. `http://dsdl-host.example.com:6060`) to exact values; never use `*` patterns, which MLflow treats as any origin. MLflow telemetry is off (`MLFLOW_DISABLE_TELEMETRY`, `DO_NOT_TRACK`).
- **API token:** `/fit`, `/apply` and the agentic chat routes accept only the exact `api_token` in the `Authorization` header (`Bearer <token>` works too), compared in constant time; 5.2.4 and the 5.2.5 test images accepted any header that contained it.
- **Agentic API (`agentic-ai`):** the chat routes `/chatbox`, `/logReview` and `/mcp/status` refuse a request that sends a wrong `api_token`. With `DSDL_AGENTIC_REQUIRE_TOKEN=true` requests without a token are refused too. The DSDL app 5.2.5 sends the token on its chat requests (`bin/chatbox_handler.py`, verified against the container certificate when one is configured) and starts containers with that setting; with an older DSDL app it is off, anyone who reaches the container's API port can use the chat and its Splunk MCP tools, and the container log warns about it. Any value other than empty, `0`, `false`, `no` or `off` turns the check on. The Splunk MCP connection and the LLM clients are set up in the background, so slow or unreachable endpoints no longer block `/fit` and `/apply`: `/mcp/status` answers at once with "start-up in progress", and a chat waits up to 20 s and then asks to retry. The MCP connection is supervised: every `DSDL_AGENTIC_MCP_RETRY` seconds (60) one that failed (refused, 401, no answer within `DSDL_AGENTIC_MCP_TIMEOUT` seconds, 60) is retried, and one that failed two MCP pings in a row (or one, when a restarted Splunk no longer knows the session) is reopened and `/mcp/status` reports it disconnected meanwhile; the chat then continues with the new tools, and a tool approval pending at that moment is dropped. When MCP tools are loaded, at start-up and after each reconnect one short tool-calling request per configured LLM provider checks that it accepts tool calls (a paid request for hosted providers): a provider that rejects it chats without tools, one that is not reachable yet, rate-limited, failing on its side (5xx) or has not answered after `DSDL_AGENTIC_PROBE_TIMEOUT` seconds (30) keeps them, and `DSDL_AGENTIC_PROBE_TOOLS=false` skips the requests. `/mcp/status` no longer returns the client configuration, there is no CORS header (the DSDL UI reaches the routes through Splunk), user and session names are sanitised before they become log file names, only the reply "yes" approves a tool call (as the prompt says), an approval is answered only by the LLM option that asked for it, and a tool call that fails (a bad SPL, or the MCP server going away) is explained instead of ending the chat; a Splunk MCP request that takes longer than `DSDL_AGENTIC_TOOL_TIMEOUT` seconds (40, at least 10) fails that way, a whole chat turn ends after `DSDL_AGENTIC_TURN_TIMEOUT` seconds (55) with a short answer, inside the DSDL proxy's 60 s, and a session answers one message at a time ("still answering" meanwhile). Bounded memory: `/logReview` reads at most 5000 events and 50 MB (`DSDL_AGENTIC_MAX_BODY_MB`), `/chatbox` at most 100 KB, and both answer with a short message beyond that (an upload of more than four times the limit is cut off); a session keeps its last 20 messages (`MAX_MSGS`) and a LangGraph checkpoint only while a tool approval is pending; sessions unused for an hour (`TTL_EVICT_SECONDS`) and the oldest beyond 500 (`MAX_SESSIONS`) are forgotten. The chat content is no longer printed to the container log; the session logs in `/srv/logs` (one file per session and day, not rotated) record each message, answer and the excerpt of the reviewed events that the LLM gets, not whole conversations or event lists. An `is_configured` of `"false"` or `"0"` now means not configured; the first entry of a service decides for its presets. Chat state lives in the API process, so the agentic image always runs one API worker, whatever `api_workers` says; a long `/fit` or `/apply` on that container (they run on the API's event loop) holds the chat until it finishes.
- **Notebooks:** eight notebooks that cannot be used as shipped in any 5.2.5 image moved to `/srv/notebooks/deprecated/` (`causalnex`, `conf25_BYO_AI_XGBoost_onnx_dsdl`, `hidden_markov_model`, `binary_nn_classifier_designer`, `binary_nn_classifier_onnx`, `dnn_regressor`, `linear_regressor`, `spacy_ner_ja`; see [notebooks/README.md](notebooks/README.md#deprecated-notebooks)). On a volume used by an earlier image their old copies stay at the top level of `/srv/notebooks`, because the start-up refresh never deletes files; delete them by hand. `/srv/notebooks/README.md` is now a shipped file (the notebook overview) and is replaced at every start: a file of your own with that name is overwritten, and backed up only on a version change.
- **Notebook backups:** `/srv/version.md` records the image version that last used the volume. On any version change, also to an older image, the shipped notebooks that the start-up refresh would overwrite and that differ from the new image (for example edited in place) are first copied into a new folder `/srv/notebooks_backup_<version>` (`.2`, `.3`, ... when the name exists). Your own notebooks, data and TensorBoard logs are never overwritten and are not copied. A volume last used by a 5.2.5 test image records the same number, 5.2.5; it is backed up too, because only these images also write `/srv/.dsdl/image-version`. Notebooks saved from a backup folder are not exported to `/srv/app/model`.
- **Accepted residual findings:** pip vendors older urllib3, msgpack and setuptools copies (4 HIGH findings in every image until pip updates them); nltk 3.10 has a HIGH finding without a fix; the llm images keep llama-index-core 0.12 (a HIGH fixed only in 0.13, which needs a code port); mlflow 3.17.1 (one HIGH in every image) and pypdf 6.21.1 (three HIGH in the llm images) were fixed upstream on 2026-10-21, after the 5.2.5 images were locked, and are updated by the next lock refresh. See [BUILD.md](BUILD.md) for the per-image results.

### Run and test your container locally
You can run your container locally, e.g. with `docker run -it --rm --name mltk-container-golden-cpu -p 5000:5000 -p 8888:8888 -p 6006:6006 -e MODE_DEV_PROD=DEV -e JUPYTER_PASSWD=<password> -v mltk-container-data:/srv splunk/mltk-container-golden-cpu:5.2.5`

**Apple silicon (Docker Desktop on a Mac):** use the arm64 images there: `golden-cpu-arm` (`golden-cpu:<v>-arm64`), and `llm-rag`, `agentic-ai` and `spark`, which are multi-platform and run natively. An amd64 image runs under Rosetta emulation, and Rosetta deadlocks in Jupyter kernels: JupyterLab opens, but a notebook stays at "Connecting" and no cell runs (the 5.2.x images show the same). `gpu` and `rapids` are amd64 only and need an NVIDIA GPU host anyway. To build an arm64 image locally: `PLATFORM=linux/arm64 ./build.sh agentic local/ <version>`.
